## The four states

| | Pause | Disable | Remove | Erase |
|---|---|---|---|---|
| `status` | `paused` | `disabled` | `removed` | `erased` |
| Sequence / AI sends | stop | stop | stop | stop |
| Manual replies | **yes** (`send-reply` allows `ok` or `paused`) | no | no | no |
| Leads in sequences | stay, continue on resume | exit `exited_sender_disabled` (status trigger) | already exited | already exited |
| Connector account | linked | **linked** (late replies arrive) | deleted; id kept in `unipile_account_id_history` | deleted |
| Cookies / extension token | kept | kept | wiped (`outreach_secret_access_log fn='sender_remove'`) | wiped |
| Paid account slot (`outreach__occupies`) | used | **used** (D7) | freed | freed |
| Conversations, `lead_sender_state`, reports | kept | kept | kept, read-only | deleted / blanked, counts kept |
| Visible in the app | yes | yes | yes, "Removed" chip, hidden from the default list | no (`deleted_at` set; reports say "Erased sender") |
| Undo | Resume | Enable | Reconnect (owner signs in again, history restored) | none |
| Who | manager+ | manager+ | manager+, or the owner by link | workspace owner |

Status changes go through `outreach_sender_pause/resume/disable/enable` (user JWT, `auth.uid()` in events and audit), `outreach_sender_remove_begin/finish` and `outreach_sender_erase_*`. Every one writes `outreach_sender_events(kind='lifecycle', data.action=…)`, `outreach_audit_log` and an outbound webhook event (`sender.paused|resumed|disabled|enabled|remove_requested|removed|erase_scheduled|erased|restored`).

**Remove is two steps.** `remove_begin` disables if needed, sets `removal_requested_at`, queues the connector delete in `outreach_account_deletions`. The edge function deletes the account; `outreach_account_deletion_result(ok)` then calls `remove_finish`, which sets `removed`, wipes credentials, drops the sender from every pool, pauses auto-enrol rules of sequences left with no active sender, cancels its import jobs and scheduled AI replies, revokes AI-reply consent and profile authority, closes reconnect tasks, frees the slot. While the connector has not confirmed, the sender stays `disabled` with "Removal pending"; the hourly billing job and the nightly housekeeping retry; managers get one email a day after six hours. Our records never say `removed` while the connector still has the account.

**Erase** needs `removed` first (the function removes when it is not), sets `erase_scheduled_at = now() + 24 h`, and F51 runs due rows: `outreach_sender_erase_storage_paths` (stored attachments + chat avatar prefixes in `outreach-attachments`) → Storage deletes recorded on `outreach_sender_erase_jobs` → `outreach_sender_erase_execute` only when nothing is left in Storage. Order and content per PRD §5.4; `actions` keep type / status / dates with `payload = '{}'`, `response = null`.

**Restore (PRD §5.1).** The connect flow already folds a second sign-in of a known profile into the existing sender (`absorbDuplicateSender`). A removed twin is a valid survivor now; `restoreIfRemoved` → `outreach_sender_restore_apply` clears the removal fields, sets `restored_at`, decays `warmup_level` by one per full 30 days away (never below 1 when it was ≥ 1). The Reconnect button on a removed sender binds the hosted link to the same row (`reconnectLink` fresh bind, same-account check), so the same path runs. Sequences, rules and pools are not restored on purpose.

**Owner link (PRD §4).** `notifySender` sends the account owner their own copy of every sender email with a footer link to `/sender-link?t=…` (`outreach_sender_owner_links`, sha256 of a 24-byte token, single use, 30 days). The page reads `outreach-sender-owner-link` (JSON) and POSTs `disconnect` (Remove with `removed_via='owner_link'`, managers emailed + `sender.owner_disconnected` event) or `erase_request` (a `follow_up` task for the workspace owner + email).

**Housekeeping (F52, nightly).** Notice 7 days before `auto_remove_at`, removal past it (`auto_after_disabled`), connector-delete retries, "removal pending" alerts, reconciliation. Reconciliation lists every connector account (paged, acts only on a complete list), logs orphans older than 24 h and senders whose account the connector no longer lists (confirmed with a direct 404) in `outreach_unipile_reconcile_log`; it deletes / marks removed only when the flag `sender_reconcile_cleanup` is `true`.

## v1.2 (26 Oct 2026): who is told, when, and the billing clock

Built from `sender-lifecycle-PRD-v2.md` in `migrations/outreach/100_sender_lifecycle_v2.sql` (`smoke_30_lifecycle_v2.sql`, 60 assertions). Emails go through [EMAIL-SENDING.md](EMAIL-SENDING.md).

**Whose account is this? (§5.8.1, D13).** Exactly one of `owner_user_id` (a member's own account: emails go to their sign-in email, read from `auth.users` at send time) or `owner_email` (someone outside: only sign-in links, permission requests, profile-change notices and disconnect notices go there, with the connecting member copied) is set (constraint `outreach_senders_one_holder`); `connected_by` is always stored. `outreach_sender_holder` / `outreach_sender_email_recipients(sender, holder|team)` resolve recipients; `outreach_sender_holder_view` is the member-facing view; `outreach_sender_set_holder(sender, {mine} | {email})` (manager+, or the member who holds it; Mine only for yourself; a teammate's email links the teammate and flags a notice) cancels open owner / consent / authority links, revokes grants with `holder_changed`, and the function `sender-lifecycle` (`set_holder`) emails the old outside address ("You're no longer the contact") and the teammate ("{name} set you as the person who signs in"). `outreach_remove_member` calls `outreach_sender_holder_left`: accounts they held pass to the connecting member, else the first owner, with a task (`node_id = 'holder_left'`) per account; their `owner_is_operator` grants end. The connect wizard asks the question (`holder` input of `sender-connect`); an outside holder gets `sender_connected_notice` once the account is connected. Owner links carry `sent_to` and die when the holder changes. **Migration of existing senders:** on this build the wizard always wrote `owner_user_id` = the connecting member and `owner_email` = the typed address, so the PRD's table was applied with `owner_user_id` read as `connected_by`: typed email = the connector's own sign-in email → Mine; another member's → that member; anyone else → Someone else's; none → Mine. Live: 2 Mine, 21 outside, 5 without an email (website inboxes) → Mine. The migration also set `settings.holder_review_pending` for a one-time "check these" banner on the senders page; the banner was dropped the same day (the guesses came from emails the team typed in, so the product owner judged the check unnecessary) and the flag cleared on the two live workspaces.

**Members only (26 Oct 2026, migration 103, overrides D13's outside option).** Every email about an account goes to a member's sign-in email; nothing goes to a typed outside address. The wizard no longer asks "Whose account is this?" (the connecting member holds it); Whose account → Change picks Mine or a teammate from the member list; `outreach_sender_set_holder` takes `{mine}` · `{user_id}` · `{email}` of a member and raises `E_HOLDER_OUTSIDE` for any other address, as does `sender-connect`. `outreach_sender_holder` never answers `outside`: a row without a member holder resolves to the connecting member, else the owners. The 21 live rows held by an outside address passed to their connecting member (`outreach_holder_member_only_backfill`, a `holder_member_only` lifecycle event keeps the old address). The column, its constraint and the outside-link machinery stay for old rows; `smoke_32` (13 assertions) and the updated `smoke_30` cover it. The senders list has no Outside badge any more.

**Disconnect alerts (§5.8).** A trigger keeps the clock on the row when a sender enters `credentials` / `error`: `disconnected_at`, `holder_notified_at`, `holder_reminders_sent`, `holder_email_held_until`, `team_notified_at`, `team_final_notified_at`; leaving to `ok` clears it and sets `last_reconnected_at`; an in-app alert `sender_disconnected` opens and resolves with it. `outreach_disconnect_holder_due` lists who is owed a sign-in email (at once for a sign-in account, after 4 silent hourly cookie retries for a LinkedIn cookie account) and the two reminders (day 1, day 3); F6 (`worker-reconnect`) only retries cookies now and hands the emails to `alerts.ts`; the `CREDENTIALS` webhook and the execute path call the same so the first email does not wait. F60 `worker-account-alerts` (dispatcher row `account-alerts`, every 15 min while an account is down): the combined team email per workspace (`outreach_disconnect_team_due`: 4 h after the sign-in email, once a day per account, the day-7 final mention, "Back online" since the last email, bounced sign-in emails flagged), the no-double-email rule (a person sees the accounts they hold only next to others; nothing when every one is theirs), and the "likely an outage" emails for holds. **Holds (§5.8.4):** 3 or more senders and 30 % or more of the workspace's live senders within 60 min → a 2 h workspace hold (`outreach_disconnect_holds`, alert `mass_disconnect`); more than 10 % of all live senders with at least 20 live and 3 drops → a platform hold (operators alerted); a platform admin extends once (`outreach_disconnect_hold_extend`). Suspended / cancelled / lapsed workspaces get no disconnect emails. The preference kind `sender_disconnected` (default on) turns the team email off per person; the outage email has no toggle.

**Pause reason (§3.2, D5).** `pause_reason` = `manual` (a person; manual replies still go out), `billing` (the workspace is suspended; `send-reply` and `outreach_sender_can_reply` refuse), `system` (health / provider warning); kept by trigger from `status_reason`. A billing pause cannot be lifted by hand (the app shows Update payment).

**Billing clock (§5.9, D15–D18).** `workspaces.billing_status` (`trialing` · `active` · `past_due` · `suspended` · `canceled` · `trial_expired`) is derived by trigger from `plan` / `stripe_status` / `past_due_since` so it never drifts; `plan` still shows `suspended` for the twenty readers that check it and `plan_before_suspension` keeps the plan name (D17's intent). The webhook records the first failed charge (`outreach_billing_payment_failed`: `past_due_since`, the hosted invoice url, `billing_action_required`) and runs the day-0 step at once; `billing_sync.ts` runs `runBillingSteps()` hourly: `outreach_billing_steps_due` (emails at 10:00 workspace time, never more than 20 h late; mechanical steps at the hour) → `outreach_billing_step_claim` (once per period) → `outreach_billing_step_apply` (`suspend` = `outreach_billing_suspend` + data date day 67 + domains paused; `remove` = every live sender removed with `billing`; `erase` = cancelled with `data_delete_after = now()`, the daily deletion path purges and emails `billing_data_deleted`). Steps: d0 payment failed · d3 reminder · d6 "sending stops tomorrow" · 7 suspended · d14 removal warning + `sender_removal_billing_notice` to each account's holder who is not a billing recipient · 21 accounts removed · d60 deletion warning · 67 erase. Recipients: owners' sign-in emails + `billing_emails` (Settings → Billing, max 5). Reactivation (`invoice.paid` for the overdue invoice, or the subscription active again): `outreach_workspace_reactivated` → senders paused for billing resume (existing), domains resume, the removed accounts' holders get `sender_reconnect_after_billing` with a sign-in link, owners get `billing_reactivated` listing accounts to reconnect and sequences without a sender. **Rollout:** the flag `billing_clock_enforce` starts `false` (emails-only mode, PRD §11 phase 5): mechanical steps are recorded and the operators alerted with the date; the existing hourly tick still suspends on day 7 when `billing_enforced` is on. Day 67 deletion also needs `billing_data_deletion`.

**Cancellation (§5.10).** `outreach__billing_cancelled` now removes every account at once (`removed_via = 'canceled'`) and keeps data 60 days (flag `billing_cancel_data_days`, was 90); `cancel_d53` sends the deletion warning 7 days before; `billing_plan_ending` goes out when `cancel_at_period_end` turns on.

**Connector (§9):** `senders_list` rows carry `holder`, `disconnected_at`, `holder_notified_at`, `holder_reminders_sent`, `holder_email_held_until`, `pause_reason`; `alerts_list` has `sender_disconnected` and `mass_disconnect`; `workspace_context` has `billing_status`, `next_billing_step`, `sending_domain`; writes on a suspended workspace return `E_BILLING_SUSPENDED`; `email_log_search` is new. No tool sets the holder.

## Deviations from the PRD, and why

| PRD | Built | Why |
|---|---|---|
| `deleted_at` is the removal time | new `removed_at`; `deleted_at` keeps meaning "hidden tombstone" (merged duplicates, erased rows) | `senders_select` hides deleted rows; a removed sender must stay visible with Reconnect and in the Removed filter |
| Every FK to `senders` → `on delete no action` + CI check | `BEFORE DELETE` trigger `outreach_sender_delete_guard`; cascades unchanged | Several child tables (events, budgets, secrets, tokens, poll plans) hang off the sender only, so `no action` would also block the workspace purge. The trigger allows: erased tombstones, never-connected placeholders, rows inside `outreach_purge_workspace` (`outreach.allow_sender_delete`) |
| `private.sender_owner_links`, `ops.unipile_reconcile_log` | `outreach_sender_owner_links`, `outreach_unipile_reconcile_log` in `public`, RLS on, no policies | the build's naming; the `private` schema does not exist here |
| Billing v2's `disconnected` next to `removed` | one state: `outreach_disconnect_sender()` is a wrapper over `remove_begin` (`trial_expired`→`trial_ended`, `user_disconnected`→`app`, billing reasons→`billing`); existing `disconnected` rows and pre-lifecycle `disabled` rows without an account were moved to `removed` | two words for "account unlinked, history kept" would have split the UI, the diagnosis and the slot count. **Behaviour change for billing:** a trial end or a 14-day billing pause now exits the leads (the PRD's remove) instead of leaving them waiting |
| Auto-enrol rules "that target this sender" | rules target sequences here: a rule is paused (`paused_reason`) when its sequence is left with no active sender; on remove it is paused, not deleted | nothing targets a sender directly; deleting a rule is not reversible |
| Duplicate live connection "stops at the wizard" and deletes the extra account | the existing fold: the new sign-in replaces the account on the one live sender, the extra connector account is deleted | one person, one record, no dead end for the owner; the unique index `outreach_senders_one_live_identity` is the database guarantee |
| "Start fresh instead" on restore | not offered; a reconnect always restores | one record per person (D10/D11); splitting history after a fold has no clean meaning. Revisit if asked |
| Scheduled AI runs → `draft_ready` on pause | status update + `flags += sender_paused`; runs still debouncing become drafts through gate G6 | the dispatch path already refuses a non-`ok` sender |
| Slot freed when the connector confirms | the slot is free as soon as the removal is requested (`outreach__occupies` ignores a sender with `removal_requested_at`) | "This frees one of your paid accounts" has to hold at click time, and the plan-limit enforcement counted on an immediate free; the connector delete is attempted at once and retried |
| (found while testing) `outreach_account_deletions_due` skipped every account a sender row still named | redefined in 096: a sender whose removal is in flight does not block its own delete | otherwise the retry queue could never finish a pending removal |
| Backlog spreading | `outreach__spread_backlog`: overdue queued actions re-dated across the next days at `effective_cap` per type per day; the tick's gaps and caps do the rest | the PRD's "within caps, never a burst" with the engine that exists |
| Trial end on a disabled sender | the billing tick now removes disabled (still linked) senders too (patched loop) | disabled keeps the link, so it would otherwise keep costing after the trial |
| Import job page "run as another sender" | not built; a paused job shows its `paused_reason` and can be cancelled / recreated | out of scope for this change |
